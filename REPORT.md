# Отчёт: вариант 2 «Кинотеатр» (Tickets + Loyalty)

Стек: Python 3.12, FastAPI, SQLite, httpx, pika, RabbitMQ 3 (`rabbitmq:3-management`), Docker Compose. Запуск: `docker compose up --build`. Скрипты прогонов лежат в `scripts/`, наборы настроек в `envs/`, результаты нагрузки в `results/`. Расширенный отчёт с таблицами и графиком — `docs/REPORT_FULL.docx`.

## 1. Что именно вы увидели на шаге 1 и почему повтор запроса создал второй билет и второе начисление?

Tickets сначала сохраняет билет и только потом синхронно вызывает Loyalty (задержка 1,5 с). Клиент с лимитом 1 с обрывает запрос, когда билет уже продан и начисление уже выполняется: операции дошли до конца на сервере, ответ 201 до клиента не дошёл. Клиент не знает, что произошло, и повторяет запрос. Для сервиса это новый запрос, места не проверяются (по условию), поэтому появляются второй билет и второе начисление. С `Idempotency-Key` ключ резервируется до обработки: повтор во время выполнения получает `409 Conflict`, повтор после завершения получает сохранённый ответ без новых билетов и начислений.

```
21:18:14,296 Ticket saved ticket_id=7a1943b7-… seat=A1
21:18:15,314 Ticket saved ticket_id=af88fda0-… seat=A1      (без ключа)
билетов на место A1: 2; баллы клиента c-nokey: 100
21:18:20,405 Idempotency-Key=key-1 is still processing, answering 409
билетов на место B2: 1; баллы клиента c-key: 50              (с ключом)
```

## 2. Какой ресурс закончился на шаге 2 и почему circuit breaker защитил Tickets лучше, чем один только таймаут?

Закончились рабочие места Tickets (4 потока): каждый вызов медленного Loyalty (20 с) занимает поток, а `/health` обслуживается тем же пулом и перестаёт отвечать. Один таймаут 1,5 с освобождает поток через 1,5 с, то есть Tickets пропускает не больше 4 / 1,5 ≈ 2,7 запроса в секунду при входящих 8: очередь растёт, ответы выходят за 5 с. Circuit breaker после пяти ошибок подряд перестаёт ходить в Loyalty, запрос завершается за миллисекунды, потоки свободны, и `/health` отвечает. Цена: пока предохранитель разомкнут, начисления не выполняются (в лог пишется предупреждение) — их надо добирать отдельно, что решает шаг 3.

```
без защиты        0/240 =   0%   /health ok 1 из 18
таймаут 1,5 с    16/240 =   7%   /health ok 1 из 18   (p50 3618 мс, p95 4706 мс)
таймаут+breaker 240/240 = 100%   /health ok 28 из 29  (p50 39 мс, p95 1582 мс)
Circuit breaker: CLOSED -> OPEN (5 consecutive failures, open for 10s)
```

Параметры breaker: порог 5 ошибок подряд (таймаут, ошибка соединения, 5xx), разомкнут 10 с, затем один пробный вызов. Жизненный цикл при остановленном и затем запущенном Loyalty:

```
21:24:11 CLOSED -> OPEN (5 consecutive failures)        Loyalty остановлен
21:24:21 OPEN -> HALF_OPEN;  21:24:29 HALF_OPEN -> OPEN (probe call failed)
21:24:39 OPEN -> HALF_OPEN;  21:24:39 HALF_OPEN -> CLOSED (probe call succeeded)
```

## 3. Что изменилось для клиента после перехода на события и какую цену вы за это заплатили?

Клиент получает 201 сразу после сохранения билета (40–80 мс), даже когда Loyalty полностью остановлен: события ждут в durable-очереди и обрабатываются после запуска сервиса. Цена: конечная согласованность (билет уже продан, баллы ещё не начислены), у клиента нет подтверждения начисления, доставка at-least-once (возможны дубли), сложнее отладка, а запись в БД и публикация события — две отдельные операции (если брокер недоступен, билет сохранён, а событие нет; лечится Transactional Outbox).

```
билет A1 (c-a1): HTTP 201 за 82 мс  "loyalty":"queued"        (Loyalty остановлен)
loyalty.ticket_sold  messages_ready=3  durable=true auto_delete=false exclusive=false
после запуска Loyalty: messages_ready=0
Accrued 50 points to customer=c-a1 for ticket=b4a4278a-… message_id=bb021b23-…
```

## 4. Почему «прибавить баллы» опасно при повторной доставке? Почему запись начисления с уникальным ticket_id проще отдельной таблицы дедупликации и почему в ней не нужна транзакция на две записи?

Доставка at-least-once: одно и то же событие может прийти дважды (потеря ack, перезапуск, ручная публикация). «Прибавить N» не идемпотентна: каждое получение увеличивает баланс, баллы удваиваются. Запись начисления с первичным ключом `ticket_id` делает дедупликацию частью самой операции: `INSERT … ON CONFLICT (ticket_id) DO NOTHING` — один атомарный оператор, повтор ничего не меняет, баланс считается как `SUM(points)` по записям. Отдельная таблица `processed_messages` потребовала бы писать две вещи (отметку и результат) в одной транзакции; здесь пишется одна строка, и атомарность даёт сама БД.

```
клиент c-dup  («прибавить», событие дважды):   100 баллов (должно быть 50)
клиент c-dup2 (ticket_id уникален, дважды):    50 баллов, записей: 1
Accrued 50 points to customer=c-dup2 for ticket=ticket-dup-2 message_id=m-dup-2
Duplicate event ignored: ticket_id=ticket-dup-2 message_id=m-dup-2 (already accrued)
```
